# 웹 유지 + React Native 앱 확장 전략 (2026)

## 1. 결론 요약

현재 구조(FastAPI + React)는 **React Native 앱으로 확장하기에 매우 유리**합니다.
특히 `backend/routers/ui.py`의 ViewModel API(`/api/ui/{user_id}/...`)가 이미 존재하므로, 앱은 웹과 동일한 백엔드 로직을 그대로 재사용할 수 있습니다.

권장 방향은 **웹 유지 + 모바일 병행 확장**입니다.
단, 앱 런칭 전에 인증/오프라인/푸시/관측성(analytics) 관련 로직을 추가하는 것이 안전합니다.

---

## 2. 왜 지금 확장이 가능한가

### 2.1 재사용 가능한 백엔드 레이어
- 인증: JWT access/refresh 구조가 이미 준비됨.
- 도메인 API: behaviors/analysis/ui 라우터가 분리되어 있음.
- 서비스 계층: 패턴 분석/AI 피드백 로직이 UI와 분리됨.

→ React Native는 화면만 다르고 API 계약은 동일하므로, 웹 로직의 60~80%를 백엔드에서 그대로 활용 가능.

### 2.2 UI API(ViewModel) 구조의 장점
- `/api/ui/{user_id}/overview`, `/analysis`, `/profile`, `/chat` 등은 모바일 화면 단위로 바로 매핑하기 쉬움.
- 앱에서 N개 API를 조합할 필요가 적어 네트워크/배터리 비용을 줄임.

---

## 3. 앱 확장 전 필수 보강 로직

### 3.1 인증/보안
1. Refresh 토큰 회전(rotating refresh token) + 재사용 감지.
2. 모바일 secure storage 사용(예: Keychain/Keystore).
3. 로그아웃 시 서버 측 토큰 무효화(blacklist 또는 토큰 버전).

### 3.2 오프라인/동기화
1. 행동 로그 임시 저장(Local queue) 후 온라인 시 재전송.
2. 충돌 정책 정의(최신 수정 우선 또는 서버 우선).
3. 네트워크 상태 감지에 따른 UX 분기.

### 3.3 성능/운영
1. API 응답 버전 관리(`/v1`) 도입.
2. 관측성: Sentry + 제품 분석(Amplitude/Firebase Analytics 등).
3. 모바일 타겟 캐싱 전략(overview/profile 30~120초).

### 3.4 제품 기능(트렌드 반영)
1. **푸시 리마인더**: 기록 유도(사용자 로컬 시간 기준).
2. **주간 요약 카드**: 감정 추세/리스크 요약 + 한 줄 액션.
3. **마이크로 코칭 루틴**: 3~5분 루틴(호흡/저널링/산책 제안).
4. **개인화 임계치**: 위험 감정 비율 임계값을 사용자별 조정.

---

## 4. React Native 구현 방식 선택

## 옵션 A) 순수 React Native 앱 (권장)
- 장점: 네이티브 UX, 푸시/백그라운드/센서 연동 유리.
- 단점: 웹 UI 코드는 직접 재사용이 적음.

## 옵션 B) Expo + React Native
- 장점: 초기 생산성 높고 배포 파이프라인(EAS) 단순.
- 단점: 특정 네이티브 모듈에서 제약 가능.

현재 팀 규모/속도를 고려하면 **Expo 기반 시작 후 필요 시 Bare 전환**이 현실적.

---

## 5. 권장 아키텍처 (웹+앱 공통)

1. `shared/` 패키지로 API 타입/도메인 모델 공통화(TypeScript 권장).
2. 웹(`frontend`)과 앱(`mobile`)에서 동일한 API 클라이언트 규격 사용.
3. 백엔드는 현재 FastAPI 유지 + API 버저닝 도입.
4. CI/CD 분리:
   - Web: Vercel/Netlify
   - API: Render/Fly.io/AWS
   - App: Expo EAS + App Store/Play Console

---

## 6. 배포까지 고려한 단계별 실행안

### Phase 0 (1~2주): 기반 정리
- API 버전 prefix 추가(`/api/v1/...`).
- 인증 토큰 정책 강화.
- OpenAPI 스키마 고정 및 에러 포맷 통일.

### Phase 1 (2~4주): 앱 MVP
- 로그인/회원가입
- 대시보드/분석/채팅/프로필 조회
- 로그 기록/수정/삭제
- 기본 푸시 리마인더

### Phase 2 (2~3주): 안정화
- 오프라인 큐 + 재시도
- 크래시/분석 SDK 도입
- 성능 튜닝(초기 로딩, 차트 렌더링)

### Phase 3 (1~2주): 스토어 릴리즈
- iOS/Android 심사 대응
- 개인정보처리방침/약관 정비
- 모니터링 대시보드 + 롤백 절차 준비

---

## 7. 유지 vs 확장 의사결정 가이드

### 웹만 유지가 맞는 경우
- 주 사용자층이 데스크톱 중심이고,
- 푸시/즉시성/일상 기록 빈도가 낮을 때.

### 앱 확장이 맞는 경우 (현재 프로젝트와 더 적합)
- 사용자 기록 행태가 "짧고 자주" 발생하고,
- 알림/개인화 코칭이 성과 지표에 중요할 때.

본 프로젝트는 행동/감정 기록 서비스 특성상 **모바일 퍼스트 사용성**이 핵심이라,
웹만 유지보다 앱 확장 시 체류/재방문 개선 가능성이 큽니다.

---

## 8. 최종 권장안

- **의사결정**: 웹 유지 + React Native(Expo) 앱 병행 확장.
- **전제조건**: 인증 강화, 오프라인 동기화, 푸시, 관측성 로직 선반영.
- **배포전략**: API 안정화 → MVP 앱 → 스토어 출시.

즉, "현재 로직만으로도 시작은 가능"하지만,
실서비스 품질과 스토어 운영까지 고려하면 위 보강 로직을 추가한 뒤 확장하는 것이 가장 안전합니다.
